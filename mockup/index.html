    End-to-end architecture

    Retrieval pattern (the key technical idea)

    1. Normalize the query (metro, tract, issue categories, time window).
    2. Embed the tenant narrative → VECTOR_SEARCH over complaints_embedded.embedding gives candidates.
    3. Hard filters win over similarity: property_type='Residential', inspection_status LIKE 'Open%', same metro, recent date.
    4. Join back to municipal_311_housing_complaints on request_id for dates, agency, coordinates, provenance.
    5. Return source metadata + match rationale + exclusion reasons (decoys are shown as rejected, with why).
    6. Never infer unit-level conditions from block/tract-level records.
    WITH cand AS (
  SELECT base.request_id, distance
  FROM VECTOR_SEARCH(TABLE a4i_housing.complaints_embedded, 'embedding',
       (SELECT @query_embedding AS embedding), top_k => 25)
)
SELECT m.request_id, m.block_address, m.raw_complaint_type, m.inspection_status,
       m.created_date, m.data_provenance, cand.distance
FROM cand JOIN a4i_housing.municipal_311_housing_complaints m USING (request_id)
WHERE m.metro_area = 'San Francisco'
  AND m.property_type = 'Residential'
  AND m.inspection_status LIKE 'Open%'
ORDER BY cand.distance LIMIT 5;

    Product guardrails

    • Evidence before answer — every claim cites a source or is labeled Tenant-reported.
    • Absence ≠ proof — “no 311 record found” never means “no problem existed”.
    • Retrieval ≠ legal determination — statutes are shown as “potentially relevant”, with conditions to confirm.
    • Human review — advocate/attorney verifies facts, law, deadlines, referrals.
    • Block ≠ unit — 100-block records are never presented as the tenant’s exact unit.
    • Non-goals — no auto-filing, no eviction prediction, no contacting landlords/courts.
